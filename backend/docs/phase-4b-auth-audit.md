# Phase 4B — Authentication & User Identity Pre-Implementation Architecture Audit

## 1. Executive Summary

This document presents a comprehensive, evidence-based pre-implementation architecture audit for **Phase 4B: Authentication & User Identity** for the School Management System (SMS) SaaS.

Following the successful completion of Phase 4A (Backend Foundation & Migration Runtime Isolation), the backend is established around Node.js 24.x, Express, PostgreSQL 16+ via Prisma, and Redis 7. Three schools have been successfully migrated into PostgreSQL:
- **SchoolS024**: `25e9637a-7fa4-4ac2-b43d-b4c0edcf2932`
- **SchoolS015**: `e2638de0-cf88-4cef-96db-74c353c6e43d`
- **SchoolS019**: `4e2c7fdf-46c1-4bc7-927f-e3382e8c579d`

### Core Audit Discoveries:
1. **Current Authentication State**: The application currently relies on client-side Firebase Authentication (`createUserWithEmailAndPassword`, `signInWithEmailAndPassword`) paired with Firestore lookups (`users/{uid}` and subcollections `schools/{schoolId}/teachers`).
2. **PostgreSQL Migrated Users (686 Total Users)**:
   - All 686 existing migrated users in PostgreSQL currently possess **`passwordHash: '!LOCKED_FIREBASE_AUTH_MANAGED'`**. This prevents unauthenticated logins until credentials are created or bridged.
   - Zero real `argon2id` hashes currently exist in PostgreSQL because Firebase Auth stores password hashes privately inside Google's infrastructure.
3. **Model Decoupling & Global Scope**:
   - `User` and `RefreshSession` are platform global models.
   - `User.schoolId` is nullable (allowing global SuperAdmin accounts and multi-school platform users while enforcing single-school tenant scoping for regular institutional users).
   - Roles (`SchoolRole`) and Permissions (`RolePermission`) are tenant-scoped and linked to users via `UserRoleAssignment`.
4. **Transition Strategy**: Phase 4B must provide a seamless, non-breaking transition mechanism supporting dual coexistence with Firebase Auth before eventual decommissioning.

        │
        ▼

   └── onAuthStateChanged(auth, async (user) => ...) [AuthContext.jsx]
        │
        ▼
[Firestore Profile Resolution: getUserProfile(uid)] [src/firebase/auth.js]
   ├── 1. Reads doc(db, "users", uid) -> { role, schoolId, email, ... }
   └── 2. If role == 'teacher' || 'staff' and schoolId present:
            ↳ Reads query(collection(db, `schools/${schoolId}/teachers`), where("userId", "==", uid))

        │
        ▼
[Role-Based Redirection]
   ├── SuperAdmin ──► /superadmin
   ├── Admin / Staff ──► /admin
   ├── Teacher ──► /teacher
   └── Parent ──► /parent

- `src/firebase/auth.js`: Implements `loginUser`, `loginWithAdmissionNumber`, `registerUser`, `logoutUser`, `resetPassword`, `getUserProfile`.
- `src/context/AuthContext.jsx`: Listens to `onAuthStateChanged`, calls `getUserProfile(uid)`, provides `useAuth()`.
- `src/pages/LoginPage.jsx`: UI form accepting email or student admission number + password.
- `src/components/ProtectedRoute.jsx`: Client-side route guard checking `userProfile.role` and module read permissions.
- `src/hooks/usePermissions.js`: Real-time listener on `schools/{schoolId}/roles` merging module permissions.

## 3. Firebase Auth User Model Audit

In the existing Firebase implementation:
- **Firebase UID**: 28-character alphanumeric string generated by Firebase Auth.
- **Email**: User's primary email address (or synthetic email `${admissionNumber}@parent.school.com`).
- **Custom Claims**: **None used**. Neither `schoolId` nor `role` are stored in Firebase Auth Custom Claims.
- **Profile Source of Truth**:
  - Roles and school associations reside entirely in Firestore documents:
    1. Root collection `users/{uid}`: `{ email, role, schoolId, createdAt, status }`
    2. Subcollection `schools/{schoolId}/teachers/{teacherId}`: `{ userId, role, roles: [], assignedClassId, staff_type }`
    3. Subcollection `schools/{schoolId}/parents/{parentId}`: `{ userId, studentAdmissionNumber, children: [] }`
- **Security Vulnerability in As-Is Flow**: Because claims are not in the Firebase ID token and Firestore security rules rely on client-supplied data, the frontend directly drives authorization routing.

## 4. PostgreSQL User Model Audit

### Prisma Schema Definition (`backend/prisma/schema.prisma` lines 90–111):
```prisma
model User {
  id                String   @id @default(uuid()) @db.Uuid
  schoolId          String?  @map("school_id") @db.Uuid
  email             String   @unique @db.VarChar(255)
  passwordHash      String   @map("password_hash") @db.VarChar(255)
  passwordAlgorithm String   @default("argon2id") @map("password_algorithm") @db.VarChar(50)
  systemRole        String   @default("TENANT_USER") @map("system_role") @db.VarChar(30)
  tokenVersion      Int      @default(1) @map("token_version")
  isActive          Boolean  @default(true) @map("is_active")
  createdAt         DateTime @default(now()) @map("created_at")
  updatedAt         DateTime @updatedAt @map("updated_at")
  legacyFirestoreId String?  @map("legacy_firestore_id") @db.VarChar(128)

  school          School?              @relation(fields: [schoolId], references: [id], onDelete: Cascade)
  refreshSessions RefreshSession[]
  staffProfile    StaffProfile?
  parentProfile   ParentProfile?
  roleAssignments UserRoleAssignment[]

  @@index([schoolId])
  @@map("users")
}
```

### Field Properties:
- `id`: UUID Primary Key.
- `schoolId`: Nullable UUID foreign key to `School.id`.
- `email`: VarChar(255), `@unique` (enforces global email uniqueness).
- `passwordHash`: VarChar(255), stores Argon2id hash or locked placeholder.
- `passwordAlgorithm`: VarChar(50), default `'argon2id'`.
- `systemRole`: VarChar(30), default `'TENANT_USER'`.
- `tokenVersion`: Integer, default `1` (enables global instant token invalidation across all user sessions).
- `isActive`: Boolean, default `true`.
- `legacyFirestoreId`: VarChar(128), stores historical Firebase Auth UID or Firestore Document ID.

## 5. RefreshSession Audit

### Prisma Schema Definition (`backend/prisma/schema.prisma` lines 113–127):
```prisma
model RefreshSession {
  id         String    @id @default(uuid()) @db.Uuid
  userId     String    @map("user_id") @db.Uuid
  tokenHash  String    @unique @map("token_hash") @db.VarChar(255)
  deviceInfo String?   @map("device_info") @db.Text
  ipAddress  String?   @map("ip_address") @db.VarChar(45)
  expiresAt  DateTime  @map("expires_at")
  revokedAt  DateTime? @map("revoked_at")
  createdAt  DateTime  @default(now()) @map("created_at")

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@map("refresh_sessions")
}
```

### Architectural Analysis:
- **Token Storage**: Stores `tokenHash` (SHA-256 hash of the cryptographically random refresh token). Raw tokens are **never** stored in the database.
- **Rotation Support**: During token refresh, the old session record is marked `revokedAt = now()` or replaced with a new record.
- **Reuse Detection**: If a revoked `tokenHash` is presented, all active sessions for that `userId` can be immediately terminated (token theft detection).
- **Session Revocation**:
  - Individual session: `UPDATE refresh_sessions SET revoked_at = NOW() WHERE id = :sessionId`
  - All sessions (global logout): `UPDATE users SET token_version = token_version + 1 WHERE id = :userId`
- **Device Metadata**: Captures `deviceInfo`, `ipAddress`, and `userAgent` for audit and session management.

## 6. Password Hashing Audit

1. **Current Implementation**:
   - `argon2` is specified in `schema.prisma` as `passwordAlgorithm = 'argon2id'`.
   - Neither `argon2` nor `bcrypt` are currently imported in runtime backend code.
2. **PostgreSQL Database State (Read-Only Verified)**:
   - **Total Migrated Users**: 686
   - **Users with `passwordHash == '!LOCKED_FIREBASE_AUTH_MANAGED'`**: **686 (100%)**
   - **Users with usable password hashes**: **0 (0%)**
3. **Rationale**:
   - Firebase Authentication hashes passwords using proprietary server-side algorithms (`SCRYPT` with Google salt/signer keys) which cannot be exported via standard client SDKs.
   - The migration safely set `!LOCKED_FIREBASE_AUTH_MANAGED` to guarantee no unauthenticated access occurs before explicit password setup or bridging.
4. **Phase 4B Requirement**:
   - Install and integrate `argon2` (or Node.js 24 native `crypto.scrypt`/`crypto.pbkdf2`) for password hashing and verification.
   - Establish password creation/migration workflows for users transitioning from Firebase Auth.

## 8. Redis Authentication Audit

| Concern | Redis Role | Classification | Justification |
|---|---|---|---|
| **Rate Limiting** | Track failed login attempts per IP and per account | **MANDATORY** | Protects against brute-force password guessing; falls back to in-memory on Redis failure. |
| **Refresh Sessions** | Primary session store | **NOT REQUIRED** | PostgreSQL `RefreshSession` table is the authoritative source of truth for persistent auditability. |
| **Session Cache** | Optional hot cache for active token versions | **OPTIONAL** | Fast O(1) lookup of `user:tokenVersion` to avoid DB query on every authenticated request. |
| **Token Blacklist** | Invalidation of prematurely revoked access tokens | **OPTIONAL** | Access tokens are short-lived (15 min); global `tokenVersion` handles full revocation. |
| **Password Reset OTP** | Temporary 15-minute OTP / password-reset tokens | **RECOMMENDED** | Ephemeral, self-expiring keys (`reset:token:<hash>`) with auto-TTL. |

## 10. Multi-Tenant RBAC Relationship

Database-backed Role and Permission model in PostgreSQL:

1. **Platform Default Template Roles**: 15 standard institutional roles seeded under `SYSTEM_TEMPLATE` school.
2. **School Roles (`SchoolRole`)**: Each school has its own role records (`schoolId`, `slug`, `name`, `loginPanel`).
3. **Role Permissions (`RolePermission`)**: Granular CRUD permissions per module (`canRead`, `canCreate`, `canEdit`, `canDelete`) linked to `SchoolRole`.
4. **User Role Assignments (`UserRoleAssignment`)**: Many-to-many junction linking `User` to `SchoolRole` within `schoolId`.
5. **Phase 4B Auth Output**: When a user authenticates, backend auth loads their active `UserRoleAssignment` records and aggregates their permissions into the token/context:
   - `req.user.roles = ['Staffs', 'Class Coordinator']`
   - `req.user.permissions = ['students:read', 'students:edit', 'attendance:mark', ...]`

## 14. Firebase → PostgreSQL Transition Analysis

```
Phase 4A (Done)             Phase 4B (Next)                     Phase 4C+ (Future)
Backend Foundation  ──►  Backend Auth Service            ──►  Full Database RBAC
                         ├── Direct Password Login            ├── Frontend Switched to Backend API
                         ├── Firebase Token Exchange (Bridge) └── Firebase Auth Deprecated
                         └── Password Set/Reset Workflow
```

### Transition Modes for Phase 4B:
1. **Direct Backend Login (New/Migrated Users with Password)**: User submits email/admission number + password -> Backend verifies Argon2id hash -> Returns Access & Refresh JWTs.
2. **Firebase Token Exchange Bridge (Coexistence Mode)**: User logs in via existing frontend Firebase Auth -> Frontend sends Firebase ID token to `POST /api/v1/auth/exchange` -> Backend verifies Firebase token, locates PostgreSQL `User`, and issues SMS Backend JWTs.
3. **First-Time Password Setup / Recovery**: User with `!LOCKED_FIREBASE_AUTH_MANAGED` uses "Forgot Password" -> Receives secure reset link -> Sets new password -> Stored as Argon2id hash.

## 18. Password Recovery & Account Reset Audit

- **Current Flow**: `ForgotPassword.jsx` sends reset email via Resend API or Firebase Auth action link.
- **Phase 4B Target Architecture**:
  1. User enters email at `POST /api/v1/auth/forgot-password`.
  2. Backend generates cryptographically secure random token (stored in Redis/PostgreSQL with 15-minute TTL).
  3. Backend dispatches email with link: `https://sms.app/reset-password?token=<raw-token>`.
  4. User submits new password to `POST /api/v1/auth/reset-password`.
  5. Backend verifies token, hashes new password with Argon2id, updates `passwordHash`, increments `tokenVersion`, and revokes all active sessions.

## 19. Login Security Requirements

| Requirement | Implementation in Phase 4B |
|---|---|
| **Brute-Force Protection** | Rate limiter on `POST /api/v1/auth/login` (e.g. 5 attempts / min per IP and per email). |
| **Timing Attack Resistance** | Use constant-time comparison (`crypto.timingSafeEqual`) during credential verification. |
| **Token Storage** | Access tokens in memory / Authorization Bearer header; Refresh tokens in `HttpOnly`, `Secure`, `SameSite=Strict` cookies. |
| **Token Expiry** | Access Token: 15 minutes; Refresh Token: 7 days. |
| **Rotation & Theft Detection** | Single-use refresh tokens; reuse of old token immediately revokes user session family. |
| **Credential Redaction** | Pino logger configured to strip `password`, `token`, `authorization` from all logs. |

## 21. Security Threat Model

| Threat | Risk | Existing Protection (Phase 4A) | Phase 4B Requirement |
|---|---|---|---|
| **Forged Access Token** | Critical | Auth middleware rejects unverified requests with 401 | Cryptographic signature verification using secret key |
| **Stolen Refresh Token** | High | Refresh sessions not yet active | Single-use rotation + reuse detection revoking session family |
| **Tenant Spoofing** | Critical | Tenant middleware rejects client `schoolId` spoofing | `req.user.schoolId` derived exclusively from verified JWT |
| **Brute-Force Password Guessing** | High | Redis rate-limiter middleware created | Apply strict rate limit (5 attempts/min) on `/api/v1/auth/login` |
| **Disabled Account Access** | Medium | `isActive` column present on User model | Explicit `isActive === true` check during login & token refresh |
| **Stale Permissions on Role Change** | Medium | Token has 15-minute expiry | Token expiry (15m) + `tokenVersion` bump on role revocation |

   - Refresh token reuse detection (triggers immediate family revocation).

   - Cross-tenant access rejection with valid token from different tenant.

## 25. Risks & Blockers

| Risk | Severity | Mitigation |
|---|---|---|
| **100% of migrated users have locked password hashes** | High | Provide password reset / setup workflow and Firebase ID token exchange bridge for seamless onboarding. |
| **Parent login via admission number** | Medium | Implement parent admission number resolver that looks up `Student` -> `ParentStudentLink` -> `User`. |
| **Missing JWT packages** | Low | Install standard `jose` or `jsonwebtoken` + `argon2` during Phase 4B package setup. |

## 26. Explicit Assumptions

1. SuperAdmin accounts have `schoolId = null` and are granted `bypassTenant: true`.
2. Institutional staff and parents belong to exactly one primary school tenant in PostgreSQL.
3. The PostgreSQL database remains the single source of truth for user roles and permissions.
4. Firebase Auth and PostgreSQL authentication will coexist during the transition period without data loss.
